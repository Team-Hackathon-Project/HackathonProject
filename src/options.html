Site access

Which quote pages the extension may re-read on its own.

Why background refresh needs this

Scanning a tab you are looking at needs no permission at all — that is what clicking the toolbar icon grants. Refreshing a ticker in the background is different: the page is not open, so the extension needs standing access to that one site. Nothing is granted at install, each host is asked for separately, and you can take any of them back here or from chrome://extensions.

Where the Scraping Browser sits in the background-refresh order.

Access

The extension needs permission to talk to the agent's address.

A real session through the Scraping Browser, repairs and all. Takes 20–35 seconds and spends Bright Data minutes. The result is stored exactly as a tab scan would be.

    Why a separate agent, and not just the extension

    The Scraping Browser is a remote Chrome addressed over the DevTools Protocol, and its endpoint carries its credentials inside the URL — wss://brd-customer-…-zone-…:password@brd.superproxy.io:9222. A browser refuses that: the HTML standard requires new WebSocket() to throw when the URL includes credentials, and the WebSocket API has no headers to carry the authentication instead. So the session runs in Node, in agent/, and this page talks to it over loopback HTTP.

    The agent runs the extension's own content script inside the remote page, so a repair made out there is the same repair the popup would have made — and it is merged back into the healed-selector registry on this machine, which is why the Selectors tab fills up whether the reading came from a tab or from Bright Data.
